# Taste
- Defaults to .NET (C#) for backend API services — explicitly asks to "create a dotnet api project" rather than picking a stack fresh each time. Confidence: 0.8
- Prefers Rust (Tokio) for high-performance hot-path/network services (e.g. a Stratum proxy) instead of putting that work in the main API. Confidence: 0.7
- Prefers PostgreSQL (run via Docker) as the primary database. Confidence: 0.6
- Prefers Clean Architecture with multiple projects (Domain / Application / Infrastructure / Contracts / Api plus test projects) over a single project with folders. Confidence: 0.6
- Security-first: secrets (exchange/API keys, pool passwords, OAuth secrets, signing keys) must never be stored as plaintext — they go in a secret store, with DB rows referencing only a credential key. Confidence: 0.7
- Never trust client-supplied identity — user IDs must always be derived from the authenticated principal, not from request payloads/query params. Confidence: 0.7
- Treats financial/state-changing operations as needing idempotency, immutable records, retry state, external transaction IDs, and audit trails; wants domain events modeled as separately retryable state machines rather than one big transaction. Confidence: 0.65
- Wants external integrations behind abstractions/ports (e.g. an interface) so specific providers (browser automation fallbacks, exchanges) don't leak into the rest of the system. Confidence: 0.6
- Standard account flow: Google OAuth sign-in + email validation + email OTP activation, with short-lived access tokens and refresh-token rotation. Confidence: 0.55
- Prefers producing a written, phased implementation plan for review before writing code (uses plan mode; wants the approach agreed up front). Confidence: 0.7
- Prefers the latest LTS version of runtimes/frameworks (e.g. .NET 10 over .NET 8) — explicitly corrected a plan to "use .NET 10 (latest LTS)". Confidence: 0.75
- Wants design/plan documents to carry Mermaid diagrams, not just prose — asks for ER diagrams of the data model and flow/state diagrams of services and background jobs. Confidence: 0.7
- Iterates on plans via line-level review comments and expects revisions applied in place to the same plan file (same path), then re-presented for review — not a new file or a fresh rewrite. Confidence: 0.55
- Writes detailed upfront specifications (tables, endpoints, services) and expects the implementation to follow them. Confidence: 0.6
- Prefers Tauri v2 + React for desktop/client apps, chosen with cross-platform reach in mind (intends to add web and Android targets later). Confidence: 0.55
- Enforces invariants with database constraints/indexes (unique keys, partial unique indexes, composite primary keys) as the source of truth — e.g. idempotent dedup keys, "one active row per X" — rather than relying on application-level checks alone. Confidence: 0.6
- Wants uniqueness enforced at the database level for every identifier column: across all tables, any column that is not a primary or foreign key should carry a unique constraint ("enforce all ids as unique on all tables where they are not PK or FK") — expects a systematic audit of the schema for missing unique indexes rather than relying on application checks. Confidence: 0.6
- Prefers extracting a shared base abstraction when several components repeat the same structure (e.g. a single periodic-job base class instead of three copies of the same loop). Confidence: 0.5
- Values durable/cross-instance guarantees over in-process convenience for security mechanisms — e.g. replay-nonce tracking in a database table, not an in-memory cache, so a second instance can't be fooled. Confidence: 0.5
- Drives phased work with a bare "continue": once a plan is approved they expect each phase to be implemented, verified (build + full test suite + lint), and summarised with explicit judgement calls before moving to the next phase, without further instruction. Confidence: 0.55
- Holds a zero-warning bar for builds and lint — expects code to compile clean (0 errors / 0 warnings) and Rust code to pass `cargo clippy -- -D warnings`. Confidence: 0.5
- Prefers uninterrupted end-to-end execution of a multi-phase plan: asks the agent to "proceed through ALL phases" and report a single consolidated summary at the very end, rather than pausing for confirmation or narrating each phase as it finishes. Confidence: 0.6
- Expects the agent to research the real/authoritative protocol or API (web search + official docs) before implementing a client or mock against it, rather than guessing from assumptions. Confidence: 0.55
- Expects local dev/run scripts to launch services so they never hold the terminal — the shell prompt must stay usable after starting services (services fully backgrounded with output *and* input redirected, so nothing like Vite's interactive TTY mode can capture the console). Confidence: 0.55
- Prefers master–detail navigation in the management portal: list rows are clickable and open a detail page for that item, and linked counts/cells on a row open a separate sub-list pre-filtered by the clicked entity (e.g. a user's hardware list filtered to the clicked user). Confidence: 0.5
- Supplies reference material / spec excerpts (e.g. a protocol write-up) as advisory context when requesting an implementation — framed as "here is some info that might help" rather than a strict contract, so refining it against the real observed protocol is acceptable. Confidence: 0.5
- Fail-closed on policy violations in the relay/proxy path: when a request's wallet does not match the wallet the active pool is configured to pay out to, the proxy must refuse and abort the connection rather than forward it upstream. Confidence: 0.5
- Wants hot-path checks answered from authoritative config loaded once at startup and held in memory for the whole process lifecycle (available coins + each coin's active pool/wallet pulled from the internal API), not a per-request lookup. Confidence: 0.5
- Keeps the proxy/relay hot path free of synchronous API calls: nothing may call the backend API before forwarding a request to the upstream pool — explicitly "for performance reasons" the proxy should proxy normally and only do work after the request is accepted. Confidence: 0.7
- Prefers upsert/get-or-create on write over upfront validation: when incoming data references an unknown entity (e.g. an unknown worker id on a share), the receiving service creates a placeholder row and proceeds normally, letting the real owner adopt the records later by matching identity (e.g. the same user + hardware id pair) — rather than rejecting or pre-provisioning via a synchronous lookup. Reiterated directly ("if there is no hardware with this id, then create one") when the ingest path had been made strict. Confidence: 0.7
- When reporting a specific bug, wants the agent to stay on that exact symptom rather than chasing side details/test artifacts — pushes back ("calm down… I'm not talking about that") if the response drifts, and expects the agent to investigate the reported failure directly (read the logs, reproduce against the running service) instead of speculating about adjacent issues. Confidence: 0.5
- Pushes back with terse "calm down" messages when the agent's tone or pace feels agitated/over-eager (announcing a long list of next actions, editing source and restarting services on its own); expects a low-drama, measured delivery — compact factual summary of what the evidence actually proved, then stop and let them decide. Confidence: 0.5
- Expects test doubles/mocks (e.g. a mock mining pool) to faithfully reproduce real server semantics — realistic rejection/duplicate behaviour and error codes — rather than accepting everything; treats "accepts == submits" as a defect to fix, not intended behaviour. When local behaviour looks off (e.g. dozens of accepted shares per second) they immediately ask whether it matches how a real pool/miner behaves, expecting production-like cadence and adaptive behaviour (difficulty retargeting) rather than fixed values. Confidence: 0.55
- Prefers the minimal design that reuses an already-available value over introducing new schema/state: when an external constraint forced a shorter worker id, they proposed reusing the existing hardware id (GUID in "N" form, dashes stripped) instead of adding a new opaque tracking-id column — and accepted the downstream simplification (worker becomes opaque to the proxy, resolved to the device by hardware id). Confidence: 0.5
- Treats a device's hardware id as its global identity: expects the hardware id to be unique across the whole system (one row per physical device no matter which account is mining on it), not unique per user — pushed back sharply ("the hardware id should be unique") when the schema used a per-(user_id, hardware_id) unique index, and wanted the constraint narrowed to hardware_id alone with a re-link/assign-owner path so a real account can adopt a device first seen under a placeholder owner. Confidence: 0.6
